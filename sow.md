# **Statement of Work: Prototype Client-Side P2P ASCII Roguelike Game**

## **I. Introduction**

This document outlines the Statement of Work (SOW) for the development of a functional prototype demonstrating a strictly client-side, peer-to-peer (P2P) multiplayer ASCII roguelike game. The primary objective is to create a baseline implementation for up to four players, showcasing core technical feasibility. Key functionalities to be developed include P2P connection establishment using a host/key model, the rendering of a shared dungeon environment, basic player representation, and real-time player movement synchronization facilitated by WebRTC technology.  
The purpose of this prototype is not to deliver a feature-complete game, but rather to serve as a technical proof-of-concept. It will validate the fundamental mechanics required for direct browser-to-browser communication and synchronized interaction within a simple game context. The resulting codebase and application are intended to guide further development efforts, potentially including those assisted by AI development tools such as GitHub Copilot, by providing a clear and working example of the core architecture.

## **II. Scope of Work**

This section details the specific features and functionalities to be implemented within the prototype.

### **A. Frontend / User Interface (UI)**

The user interface will be minimal, focusing solely on enabling the core game connection and interaction flows.

* **A.1 Landing Page:** A simple HTML page will serve as the entry point. It must contain two primary interactive elements: a button labeled "Create World" and a button labeled "Join World". No other complex navigation or informational elements are required on this initial page.  
* **A.2 "Create World" Flow:**  
  1. Upon clicking the "Create World" button, the application will initiate the necessary logic to establish this browser instance as the host peer for a new game session.  
  2. A unique session key (e.g., a short alphanumeric string) must be generated and prominently displayed to the user who initiated the creation. This key is the identifier required for other players to join this specific session.  
  3. Simultaneously, the UI will transition to display the main game view, rendering the initial state of the ASCII dungeon environment.  
* **A.3 "Join World" Flow:**  
  1. Clicking the "Join World" button will reveal an input field prompting the user to enter a session key.  
  2. Upon submission of a key entered into this field, the application will attempt to locate and establish a P2P connection with the host peer associated with that specific key via the configured signaling mechanism.  
  3. If the connection is successfully established, the UI will transition to display the main game view, rendering the shared ASCII dungeon environment as received from the host or generated locally based on session parameters. If connection fails, minimal feedback (e.g., an alert or message) should indicate the failure.  
* **A.4 Main Game View:** This core UI component consists of a designated area responsible for rendering the game state. It must display a grid representing the ASCII dungeon layout, including walls and floor tiles. Within this grid, it must also render the player characters, represented by the '@' symbol, at their respective coordinates.

### **B. Connection and Networking (WebRTC)**

The networking layer relies exclusively on WebRTC for direct peer-to-peer communication, eliminating the need for a central game server beyond initial signaling.

* **B.1 WebRTC Integration:** The project requires the selection and integration of a suitable mechanism to manage WebRTC connections. This can be achieved either by utilizing a higher-level library, such as PeerJS (v1.x or latest stable recommended for simplicity), or by directly implementing the necessary logic using the native browser WebRTC APIs (RTCPeerConnection, RTCDataChannel). The chosen approach must effectively handle the creation and management of P2P connections between the host and clients.  
* **B.2 Signaling Mechanism:** A signaling mechanism is essential for peers to exchange metadata (like SDP offers/answers and ICE candidates) needed to establish a direct connection.  
  * The primary recommended approach is to utilize a free, public signaling server, such as the default server provided by PeerJS. This simplifies setup considerably.  
  * The session key generated by the host (Section II.A.2) will serve as the rendezvous identifier. Clients will use this key to find the corresponding host via the signaling server.  
  * An alternative, simpler (but less user-friendly) mechanism involves the manual exchange of SDP offers/answers between users alongside the session key. This avoids reliance on a public signaling server but places the burden of metadata exchange on the users themselves. This approach is acceptable for the prototype if the public server approach proves problematic, but is not preferred.  
  * Regardless of the method, integration with public STUN servers (e.g., stun:stun.l.google.com:19302) is mandatory within the RTCPeerConnection configuration to facilitate NAT traversal. Initial setup will exclude TURN servers.  
* **B.3 Host Logic ("Create World"):** The browser instance initiating "Create World" assumes the host role. Its responsibilities include:  
  * Initializing itself as a WebRTC peer using the chosen library or API.  
  * Generating a unique session key and associating it with its own peer ID on the signaling server (if used).  
  * Actively listening for incoming connection requests from potential clients that target its specific session key/peer ID.  
  * Managing P2P connections for up to three joining clients, ensuring a maximum of four peers (1 host \+ 3 clients) in the session.  
* **B.4 Client Logic ("Join World"):** A browser instance attempting to "Join World" acts as a client. Its responsibilities include:  
  * Initializing itself as a WebRTC peer.  
  * Using the session key entered by the user to identify and connect to the corresponding host peer through the signaling mechanism.  
* **B.5 Data Channels:** Once a P2P connection is established between the host and a client, a reliable WebRTC data channel (RTCDataChannel) must be opened over this connection. These data channels form the communication backbone for transmitting game-related information, such as player inputs and game state updates, between peers. Reliability ensures that game messages are delivered in order.

### **C. Game Logic (Client-Side)**

All game logic is executed directly within the client browsers.

* **C.1 Static Dungeon Generation:**  
  * A simple dungeon generation function must be implemented in JavaScript. This function will create a static, single-room layout represented as a 2D grid.  
  * The layout should be fixed-size (e.g., 40x25 cells) and consist of wall characters ('\#') forming a border and floor characters ('.') filling the interior space.  
  * Crucially, this function must be *deterministic*; it must produce the exact same grid layout every time it is executed without any external input.  
  * This deterministic function runs independently on the host's machine when the world is created and on each client's machine immediately after successfully joining the session. Executing this identical function on all peers ensures that every participant starts with the same base map structure without requiring the host to transmit the entire map data over the network. This significantly simplifies the initial state synchronization process, as only dynamic elements (like player positions) need active network synchronization.  
* **C.2 Player Representation:**  
  * Each connected player will be visually represented on the ASCII grid using the '@' symbol.  
  * To distinguish players, each '@' symbol must be assigned a unique and persistent color. This can be achieved using CSS classes or inline styles applied to the character element.  
  * The host will manage color assignment upon player connection (e.g., Host \= Red, Client 1 \= Blue, Client 2 \= Green, Client 3 \= Yellow). This player-color mapping information will be communicated from the host to all clients as part of the regular game state updates (see Section II.D).  
* **C.3 Player Movement Logic:**  
  * The application must capture keyboard input events, specifically for the Arrow Keys (Up, Down, Left, Right).  
  * Client-side JavaScript logic will translate these key presses into intended movement actions (e.g., pressing 'ArrowUp' signifies an intent to move one cell upwards).  
  * The client application should *not* update the player's position on its local display immediately upon detecting a key press. Instead, it must package the movement intent into a message and send it to the host peer via the WebRTC data channel (detailed in Section II.D.2). Any form of client-side prediction or immediate local movement execution is explicitly excluded from this prototype to maintain the purity of the host-authoritative model. Basic client-side input filtering (e.g., rate limiting) may be implemented, but authoritative validation resides solely with the host.

### **D. State Synchronization**

A host-authoritative model will be used to maintain a consistent game state across all connected peers.

* **D.1 Synchronization Model:** The peer that initiated the session ("Create World") acts as the single source of truth (authority) for the game state. In this prototype, the game state primarily consists of the current position of all player characters.  
* **D.2 Client Input Transmission:** When a client player presses a movement key, the client application constructs a message containing the intended action (e.g., a JSON object like { action: 'move', direction: 'up' }). This message is then sent directly to the host peer using the established reliable WebRTC data channel.  
* **D.3 Host State Validation and Update:** The host peer continuously listens for incoming movement input messages from all connected clients on their respective data channels.  
  * Upon receiving an input message, the host validates the requested move against its authoritative version of the game state. Validation checks must include:  
    * Ensuring the target coordinate is within the defined dungeon boundaries.  
    * Ensuring the target cell is not a wall ('\#').  
  * If the move is deemed valid according to these rules, the host updates its internal game state representation by changing the position of the player who sent the input.  
  * If the move is invalid (e.g., moving into a wall), the host simply ignores the input message; no state change occurs, and no specific error message needs to be sent back to the client for this prototype.  
  * The host also processes its own movement inputs directly against its authoritative game state, applying the same validation rules.  
* **D.4 Game State Broadcasting:** After processing any valid movement inputs (either from itself or from clients) and updating its internal state, the host must broadcast the *complete and current state* of all player positions to *all* connected clients.  
  * This broadcast should occur whenever the state changes. For simplicity in this prototype, sending updates immediately after processing a valid move is sufficient.  
  * The broadcast message should contain a comprehensive list of all currently connected players, their unique identifiers (which could be their peer IDs or a simpler assigned ID), their current X/Y coordinates, and their assigned color. An example format could be: { type: 'gameStateUpdate', players: \[{ id: 'hostPeerId', x: 5, y: 5, color: 'red' }, { id: 'client1PeerId', x: 10, y: 8, color: 'blue' }\] }.  
  * Broadcasting the entire state in every update message is a straightforward approach suitable for this prototype due to the small number of players (max 4\) and the minimal state being synchronized (just positions). This avoids the complexity of implementing delta compression or event-based synchronization. However, it's important to recognize that this method does not scale efficiently to games with larger player counts or more complex states, where it would consume unnecessary bandwidth and processing resources.  
* **D.5 Client State Reception and Rendering:** Client peers listen for gameStateUpdate messages arriving from the host on their WebRTC data channel.  
  * Upon receiving such a message, the client **must discard its previous understanding of player positions** and update its local game state representation strictly based on the data provided by the host.  
  * The client then re-renders the main game view (Section II.A.4) to accurately reflect the authoritative positions and colors of all players as dictated by the host's latest update. This approach makes clients effectively "dumb renderers" of the host-provided state. While ensuring consistency across all peers and simplifying client logic, this host-authoritative model inherently introduces latency: a client's action is only visually reflected after the input travels to the host, is processed, and the resulting state update travels back to the client. Mechanisms like client-side prediction to mitigate this perceived lag are explicitly excluded from this prototype. Furthermore, the host acts as a central point for game logic processing, which increases its computational load with more players, and represents a single point of failure for the game session's progression.

## **III. Technical Specifications**

The prototype will be developed using standard web technologies.

* **3.1 Frontend Technologies:**  
  * HTML: HTML5  
  * CSS: CSS3 (minimal styling for layout and player color differentiation is sufficient)  
  * JavaScript: ECMAScript 6 (ES6) or later. Vanilla JavaScript is preferred to minimize dependencies. However, the use of a simple, lightweight frontend framework (e.g., Svelte, Vue.js, React) is permissible if the development team (human or AI) determines it significantly accelerates the implementation of the required UI components (Section II.A) without introducing undue complexity.  
* **3.2 Networking Technologies:**  
  * Peer-to-Peer Protocol: WebRTC. Implementation can use a library (e.g., PeerJS) or native browser APIs (RTCPeerConnection, RTCDataChannel).  
* **3.3 Signaling & NAT Traversal:**  
  * Signaling: A public PeerJS server (using its default configuration) is the recommended solution. Manual SDP/ICE exchange is a fallback option.  
  * STUN (Session Traversal Utilities for NAT): Utilization of publicly available STUN servers (e.g., stun:stun.l.google.com:19302) is required and must be configured in the RTCPeerConnection setup.  
  * TURN (Traversal Using Relays around NAT): Usage of TURN servers is explicitly excluded from the initial scope due to complexity and cost implications. Development will proceed assuming STUN is sufficient for NAT traversal in typical test environments.

## **IV. Project Deliverables**

The project will result in the following deliverables:

* **4.1 Source Code:** The complete, unobfuscated source code for the web application, including all HTML, CSS, and JavaScript files necessary to implement the features defined in Section II. The code should be reasonably well-organized and include comments sufficient for another developer to understand the key logic sections, particularly concerning WebRTC setup, signaling, data channel communication, and state synchronization. Delivery via access to a Git repository is preferred.  
* **4.2 Deployable Build:** A set of static files (HTML, CSS, JS bundle if applicable) that constitute the functional prototype. These files must be capable of being served by any standard static file server (e.g., Python's http.server, npx serve, Nginx, Apache) and run directly in compatible web browsers. The deployed build must allow users to host and join games as described in Section II.  
* **4.3 Runtime Instructions:** A basic README.md file containing clear, concise instructions covering:  
  * Steps required to serve the static files locally for testing.  
  * How to open the application in a web browser.  
  * A simple walkthrough guiding a user through creating a world, obtaining/sharing the key, and having another user join that world.  
  * Any known major limitations or browser compatibility requirements (e.g., requires Chrome/Firefox version X+).

## **V. Assumptions and Exclusions**

This section outlines the underlying assumptions for the project and explicitly lists features that are out of scope.

### **A. Assumptions**

* **A.1 Developer Familiarity:** The developer (human or AI) undertaking this work is assumed to possess foundational knowledge and practical experience with HTML5, CSS3, modern JavaScript (ES6+), and the core concepts of WebRTC, including RTCPeerConnection, RTCDataChannel, and the role of signaling.  
* **A.2 Environment:** Development and testing will be conducted using modern desktop web browsers that provide robust WebRTC support (e.g., latest stable versions of Google Chrome, Mozilla Firefox). Compatibility with older browsers or mobile browsers is not a requirement.  
* **A.3 Signaling/STUN Access:** The project assumes reliable access to the internet and the continuous availability of the chosen public signaling service (e.g., the default PeerJS server) and public STUN servers during development and testing. No provision will be made for hosting custom signaling or STUN/TURN infrastructure.  
* **A.4 Network Conditions:** Development and testing assume reasonably stable network conditions between peers, without significant packet loss, jitter, or excessive latency. The prototype will not include mechanisms for handling or mitigating poor network conditions gracefully.

### **B. Exclusions**

Defining what is *not* included is crucial for managing the scope of this prototype. The following features and functionalities are explicitly **out of scope**:

* **Game Mechanics:**  
  * Complex dungeon generation (e.g., procedural algorithms, multiple interconnected rooms, different levels).  
  * Items, equipment, or an inventory system.  
  * Combat mechanics (player vs. player or player vs. environment).  
  * Non-player characters (NPCs), including monsters or other entities.  
  * Defined game objectives, win/loss conditions, scoring, or progression systems beyond basic movement.  
* **Networking Robustness:**  
  * Sophisticated error handling for network issues (e.g., temporary disconnections, packet loss).  
  * Connection state management beyond initial establishment (e.g., detecting and handling peer disconnections, implementing reconnection logic).  
  * Implementation or configuration of TURN servers for relaying traffic in challenging NAT scenarios.  
  * Bandwidth optimization techniques (e.g., reducing the frequency or size of state updates).  
* **Synchronization Complexity:**  
  * Advanced state synchronization strategies such as delta compression (sending only changes), client-side prediction, server reconciliation, or lag compensation techniques.  
  * Synchronization of any game state other than player X/Y coordinates and color.  
* **User Experience:**  
  * In-game text chat or other communication features.  
  * Advanced user interface elements, visual polish, animations, or sound effects.  
  * Persistence of user identity, settings, or game state across browser sessions or refreshes.  
* **Security & Anti-Cheat:**  
  * Measures to prevent cheating (e.g., host authority validation, sophisticated input validation).  
  * Secure key exchange mechanisms beyond the simple display and manual sharing described.  
* **Scalability:**  
  * Performance optimization or testing for scenarios involving more than four simultaneous players.  
  * Design considerations for handling significantly more complex game states.

Establishing these exclusions ensures that development efforts remain focused on the core objective: demonstrating basic P2P connectivity and state synchronization using WebRTC for a simple multiplayer experience. This focus is essential for delivering a functional proof-of-concept within a reasonable timeframe.  
The following table categorizes the primary feature exclusions:

| Category | Excluded Features | Rationale |
| :---- | :---- | :---- |
| Core Gameplay | Combat, Monsters, Items, Inventory, Multiple Levels/Rooms, Procedural Generation, Game Objectives | Focus on core P2P connection & sync |
| Networking & Robustness | Disconnect/Reconnect Logic, TURN Server Usage (initially), Advanced Error Handling, Bandwidth Optimization | Prototype simplicity, focus on basic path |
| Synchronization | Client-Side Prediction, Lag Compensation, Delta Updates, Non-Position State Sync | Basic host-authority model sufficient for PoC |
| User Experience | Chat, Sound, Animations, Advanced UI, Persistence (Save/Load) | Non-essential for core technical validation |
| Security & Anti-Cheat | Cheat Prevention, Secure Key Exchange | Out of scope for prototype functionality |
| Scalability & Performance | Optimization beyond 4 players | Focus on small-scale P2P interaction |

## **VI. Conclusion**

This Statement of Work defines the requirements for building a prototype client-side P2P multiplayer ASCII roguelike game. The successful completion of this project will yield a functional application demonstrating essential WebRTC-based multiplayer mechanics: host/client connection via a key system, rendering of a shared static environment, and host-authoritative synchronization of player movement for up to four participants. The resulting source code and deployable build will serve as a valuable technical baseline and feasibility study, informing potential future development of more complex P2P web-based games. Adherence to the specified scope, technical specifications, and exclusions is paramount to achieving the project's objectives efficiently.
